PCC Device Intake

One question per field. Fields marked "never defaulted" or "sensitive" are never guessed or filled in for you — an empty answer blocks the step that needs it. Fields marked "self-declared" record only what you attest, never a researched or inferred value. An evidence badge marked "stub" proves nothing yet: the vocabulary defines it, but no verifier is live for it today.

Identity

operator.displayName
What name should buyers see as the operator of this device?
This is the name that appears on every listing and job you accept.
class C
required for: register
operator.contactEmail
What email should account and job notices go to?
We need a channel to reach you about jobs, approvals, and account security.
class C
required for: register
operator.authority
Is this device yours to offer, or are you setting it up for someone who decides about it?
Only the person who controls a device can offer it for work — this is never assumed.
class C never defaulted
required for: register
If you don't know: Pause here and check with whoever owns or controls this device before continuing — don't guess or decide on someone else's behalf.

Device

device.description
In your own words, what is this device and what should buyers expect to get from it?
This seeds device identification and the search for a matching capability contract.
class C
required for: identify
If you don't know: Take a photo of the label and describe whatever you see — a rough guess of what it does is enough for the agent to search from.
device.vendor
Confirm the device's manufacturer/vendor.
The vendor name drives the adapter config and which kits can match this device.
class A
required for: register-device
If you don't know: the agent will research this (see "identify-make-model" in the research library)
device.model
Confirm the device's exact model.
The exact model is how we find the right manual, safety limits, and remote-control protocol.
class A
required for: register-device
If you don't know: the agent will research this (see "identify-make-model" in the research library)
device.serialNumber
What is the device's serial number (from its label)?
The serial number ties this specific unit to its device record.
class C
required for: register-device
If you don't know: Look for a printed serial number on the device's data plate or a sticker near the power input. If it truly has none, say so.
device.firmware
Confirm the device's firmware version.
Firmware version affects which commands and safety behaviors are available (N83 G8).
class A
required for: register-device
If you don't know: Check the device's display, status page, or companion app's "About" or "System Info" screen for a firmware or software version.
device.adapterType
Confirm the adapter type PCC should use to talk to this device.
This selects the real adapter that will run jobs — it is never "mock" for a live device.
class A
required for: register-device
If you don't know: the agent will research this (see "find-remote-interface" in the research library)

Location

location.cityCountry
What city and country is this device located in? (Shown publicly on your listing.)
Buyers need this to judge shipping time and jurisdiction — it's shown publicly, so keep it to city and country, never a street address.
class C
required for: publish
location.streetAddress
What is the device's street address? (Private — never shown publicly; used for logistics only.)
We need this for couriers and installers, but it is never published — public listings only ever show city and country.
class C sensitive: do not write it here
required for: optional

Network

network.reachability
Is this device on the same local network as the agent host, and does it have a static IP?
This decides whether we can reach it directly or need pcc-node as a relay.
class C
required for: register-device
If you don't know: Ask whoever manages your network whether this device has a fixed IP, and whether it's on the same network segment as the machine running the agent.
network.outboundHttps
Can this device (or its host) make outbound HTTPS calls?
Outbound-only connectivity lets us use pcc-node without opening any inbound ports.
class C
required for: register-device
If you don't know: Try loading any https:// page from a browser on the same network as the device — if that works, outbound HTTPS is very likely allowed.
network.inboundBlocked
Is inbound access to this device blocked by a firewall or NAT?
This confirms whether pcc-node's outbound-only design is required.
class C
required for: register-device
If you don't know: Ask whoever manages your router or firewall whether inbound connections to this device are blocked — most home and office routers block inbound by default.

Safety

safety.supervision
When it runs a job, will someone be nearby, or will it run unattended? If someone's nearby, who?
Supervision level is never assumed — it directly bounds which jobs are safe to accept.
class C never defaulted
required for: publish, accept-jobs
If you don't know: Decide whether someone will be physically present, watching remotely, or nobody at all while a job runs — this is a decision only you can make.
safety.estop
How do you stop this device in an emergency — for example a stop button, a power switch, or a lid switch — and where is it?
Before anything runs, we need a way to stop it that doesn't depend on software — this is never assumed.
class C never defaulted
required for: publish, accept-jobs
If you don't know: the agent will research this (see "find-safety-limits" in the research library)
safety.hazards
What hazards does this device present (chemical, laser, heat, mechanical, biological)?
Hazard classes shape the safety envelope — an empty answer blocks job acceptance rather than assuming "none".
class C never defaulted
required for: accept-jobs
If you don't know: the agent will research this (see "find-safety-limits" in the research library)
safety.limits
Here are the safety limits we found for this device, with where each came from — confirm each one, or correct it.
The device refuses any operation outside these limits, so they must be right for your unit — never a guess.
class B never defaulted
required for: accept-jobs
If you don't know: the agent will research this (see "find-safety-limits" in the research library)
safety.commandRate
At most how many commands per minute may PCC send to this device?
The safety envelope refuses commands faster than this, so a runaway job can't overload the device.
class C never defaulted
required for: accept-jobs
If you don't know: the agent will research this (see "find-safety-limits" in the research library)

Calibration

This is self-declared only — we never infer or default a calibration date.
class C self-declared evidence: decl.self_attested (live)
required for: tier1
If you don't know: Check your maintenance log or the device's calibration sticker. If you're still not sure, calibrate it now and record today's date.

Evidence

evidence.executorDeviceId
Which device id actually executes the job?
This is the raw fact the evidence plan is built from — independence is derived from it, never asked directly.
class C
required for: tier1
If you don't know: Name the device id of the machine that actually performs the job — not a camera or sensor only watching it.
evidence.observerDeviceIds
Which device ids (if any) only observe the job, without executing it?
An observer that isn't also the executor is what makes an inspection independent — we derive that, we don't ask you to assert it.
class C
required for: tier1
If you don't know: List the device ids of any camera or sensor that watches the job without controlling it. Leave it empty if nothing else observes.
evidence.executionMode
Is this run against the real device, or a mock/dry-run adapter?
A mock or dry-run answer caps the job's evidence at tier 0 — it can lower the tier, never raise it.
class A evidence: confirm.execution_mode (live)
required for: tier1
evidence.camera
Where could a camera see this job's result — does it see the work area, does it see the output, is it fixed or handheld, and which device id captures it?
Buyers pay against evidence that the work happened, and what the camera can see decides how strong that evidence is.
class C evidence: capture.photo_nonced (stub — stub = proves nothing yet)
required for: tier2
If you don't know: Look for a camera already pointed at the work area or output — a webcam, a phone on a stand, a security camera. If there isn't one yet, say so; the agent can suggest a placement.
evidence.operatorPresence
Is an operator present always, sometimes, or never during a job?
Operator presence shapes what kind of evidence and approval is realistic to collect.
class C
required for: tier1
If you don't know: Think about your usual routine: are you standing at the device while it runs, checking in occasionally, or away entirely?
evidence.approver
Who is the person who will approve evidence for this device? (identity only — their signing key is registered separately later.)
We need to know who will attest to job quality before we register how they sign.
class C evidence: approval.expert (stub — stub = proves nothing yet)
required for: tier2
If you don't know: Name the specific person who will review job evidence for this device — a name and contact, not a role or team.
evidence.controllerRunLog
Can the controller export its own execution log per job? If so, via API or file?
A per-job exportable log is what lets us build a trustworthy machine execution record.
class C evidence: machine.execution_log (stub — stub = proves nothing yet)
required for: tier1
If you don't know: the agent will research this (see "find-evidence-signals" in the research library)
evidence.instrumentSignsOutput
Does the instrument cryptographically sign its own output?
A self-signing instrument raises the evidence ceiling — but only once its signing key is registered (companion primitive: receipt.kernel_signed).
class C evidence: ident.registered_key (stub — stub = proves nothing yet)
required for: tier1
If you don't know: the agent will research this (see "find-evidence-signals" in the research library)
evidence.referenceSample
Do you have a reference sample with a known expected result?
A known-good test pair is the strongest cheap proof that the capability actually works.
class C evidence: measure.io_test_pair (stub — stub = proves nothing yet)
required for: tier1
If you don't know: Check whether you have a past output with a known-good result to compare a new job against. If not, say so — this proof method just isn't available yet.

Pricing

pricing.unitPrice
What should one job cost? During the public beta, payments settle on a test network, so no real money moves yet.
Only you decide what your work costs — this is never assumed or guessed.
class C never defaulted
required for: publish
If you don't know: Look at what comparable services charge as a reference point, then decide your own price — a reference is never the answer itself.
pricing.minimum
Is there a minimum charge per job?
A minimum protects you from unprofitable small jobs — never assumed.
class C never defaulted
required for: publish
If you don't know: Decide whether a small job would be unprofitable at your per-unit price. If so, set a minimum; if not, say there isn't one.
pricing.currency
What currency is your price in?

class C never defaulted
required for: publish

Payout

payout.destination
Which wallet address should your payments go to? (During the beta this is a test-network address. Never a private key or recovery phrase.)
Your earnings go only where you say — this is never assumed, and the address itself is never written into this record; it goes straight to the payout store.
class C never defaulted sensitive: do not write it here
required for: get-paid
If you don't know: Have your wallet address ready (a test-network address during the beta). Never type a private key or recovery phrase here.

class C
