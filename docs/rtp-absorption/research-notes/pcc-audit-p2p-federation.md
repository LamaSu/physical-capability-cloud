## PACKAGE: @pcc/dht

**Files audited:**
- `packages/dht/src/dht-node.ts` — DHTNode class (328 lines)
- `packages/dht/src/transport.ts` — DHTTransport wrapper (145 lines)
- `packages/dht/src/registry.ts` — AnnouncementRegistry (213 lines)
- `packages/dht/src/announcement.ts` — createAnnouncement / verify (59 lines)
- `packages/dht/src/query.ts` — CapabilityQuery filter + ranking (155 lines)
- `packages/dht/src/bootstrap.ts` — bootstrap node loader (49 lines)
- `packages/dht/src/telemetry.ts` — DHTTelemetry EventEmitter (175 lines)

### What it is

A **custom gossip-flood DHT** with NO Kademlia routing. The comment at
`dht-node.ts:19` states this explicitly:

> "The DHT is intentionally simple — no Kademlia routing, no CRDTs, just
> gossip. This keeps it lightweight enough to run on operator hardware."

Protocol mechanics:
1. **Announce**: broadcast signed `CapabilityAnnouncement` to all connected
   peers with a TTL (default 3 hops). Each peer re-broadcasts with TTL-1 until
   TTL=0 (`dht-node.ts:285-293`).
2. **Query**: broadcast a `CapabilityQuery` to all peers, collect
   `query_result` responses within a configurable timeout (default 3s)
   (`dht-node.ts:118-175`).
3. **Heartbeat / prune**: announcements expire via TTL on the
   `AnnouncementRegistry` (`registry.ts:43-55`).

Message types (`transport.ts:30-36`):
```
announce | query | query_result | peer_list | ping | pong
```

The **protocol identifier** is `"/pcc/cap-gossip/1.0.0"` (`transport.ts:28`).

### What it stores / routes

- **Primary**: `CapabilityAnnouncement` records, keyed by `kernelDid`, with
  per-announcement TTL (`registry.ts:72`).
- **Secondary**: `EvidenceAnnouncement` records (IPFS CID + Lit Protocol access
  conditions), keyed by `bundleId`, with a fixed 1-hour TTL
  (`registry.ts:151-161`). The registry stores these but the DHT gossip protocol
  (`DHTMessage` union in `transport.ts:30-36`) does NOT have a message type for
  evidence announcement gossip — they can only be stored locally via
  `registry.storeEvidence()` and queried locally.
- **NOT stored**: jobs, evidence payloads, wallet addresses.

### Can it carry payloads?

**DISCOVERY-ONLY for the gossip path. No evidence bundle transport.**

The DHT can gossip `CapabilityAnnouncement` objects containing endpoint metadata
(URLs). A node learning of a kernel learns where to connect — but the connection
itself (job dispatch, evidence upload) flows through the PCC gateway's HTTPS
API, not through the DHT.

Evidence announcements (`EvidenceAnnouncement`) are stored in the registry's
`evidenceStore` map (`registry.ts:39`) but there is NO `DHTMessage` type for
gossiping them to peers. They can only arrive via `registry.storeEvidence()`
called locally (e.g., from gateway code after a LIT Protocol upload). No
peer-to-peer evidence propagation exists.

Pub/sub: none. Direct messaging: none. The only message exchange is:
- node-to-all (broadcast announce/query)
- node-to-one (query_result reply, ping/pong)

### Addressing

- **Peer identity**: `PeerIdentity.did` — `"did:pcc:<id>"` format
  (`spec/src/types/p2p.ts:7`).
- **Transport-layer peer IDs**: opaque string generated by `CoreTransport`
  in pattern `"peer_<label>_in_<N>"` / `"peer_<label>_out_<N>"`
  (`dht-core/src/transport.ts:90,105`).
- **Peer→DID mapping**: `DHTNode.getPeers()` returns synthetic DIDs from
  transport peer IDs, not verified identities (`dht-node.ts:181-186`).
- **PeerEndpoint.transport** type (`spec/src/types/p2p.ts:50`):
  `"websocket-direct" | "websocket-relay" | "webrtc" | "http-poll"` — but only
  `"websocket-relay"` and direct WebSocket are implemented.
- No wallet address routing. No Ethereum/EVM address in peer identity.

### NAT traversal

**NONE implemented.**

- Bootstrap node: `wss://capability.network/ws/dht` (`bootstrap.ts:11`).
  The cloud gateway acts as the relay/rendezvous point.
- LAN/local: `ws://192.168.1.10:9090` is shown as an example config
  (`bootstrap.ts:19`) but requires operator-opened ports.
- No TURN/STUN, no WebRTC ICE, no hole-punching, no relay forwarding.
- `TransportType` includes `"webrtc"` (`p2p.ts:50`) but no WebRTC code exists.

### Gateway integration

`packages/gateway/src/routes/dht-ws.ts` wires the DHT:
- `GET /ws/dht` — WebSocket endpoint, auth-gated (Bearer `pcc_...`)
  (`dht-ws.ts:49-61`)
- `GET /api/dht/query` — REST query fallback
- `POST /api/dht/announce` — authenticated kernel announcement
- `GET /api/dht/peers` — peer list + registry stats
- `GET /api/dht/metrics` — telemetry snapshot
- `GET /api/dht/events/stream` — SSE live event stream

The gateway's DHTNode configures itself as a bootstrap peer
(`bootstrapNodes: []`, `port: 0`, `dht-ws.ts:33-36`) and injects externally
provided WebSockets into the transport via `handleConnection(socket)`.

## PACKAGE: @pcc/dht-core

**Files audited:**
- `packages/dht-core/src/transport.ts` — CoreTransport (222 lines)
- `packages/dht-core/src/identity.ts` — PeerIdentity helpers (116 lines)
- `packages/dht-core/src/peer-manager.ts` — KnownPeer registry (142 lines)

### What it is

A **shared WebSocket transport primitive** library. Extracted from `@pcc/dht`
so the federation runtime can use the same wire primitives without dragging in
gossip-specific message types.

`CoreTransport` (`transport.ts:63-221`):
- Wraps `ws` (the Node.js `ws` package) for server and client sockets
- `listen(port)` → starts `WebSocketServer`
- `connect(url)` → dials outbound WebSocket
- `adoptSocket(ws)` → accepts externally-provided socket
- `send(peerId, CoreMessage)` / `broadcast(CoreMessage, exclude?)`
- `CoreMessage` is `{ protocol: string; payload: unknown }` — multi-protocol
  multiplexing on the same connection via `protocol` field (`transport.ts:32`)

`PeerManager` (`peer-manager.ts`):
- In-memory known-peer registry with allowlist mode
- Tracks: DID, identity, lastSeenMs, rttMs, errorCount
- Two modes: open (gossip DHT, all peers allowed) vs allowlist (federation,
  explicit allow per `setAllowed()`)

`identity.ts`:
- Helpers for DID→peerId derivation, `PeerEndpoint` sort/compare/prefer
- `canonicalIdentityJson()` for signing purposes

**No NAT traversal, no discovery, no crypto. Pure WebSocket frame transport.**

## PACKAGE: @pcc/federation

**Files audited:**
- `packages/federation/src/index.ts` — package scope declaration
- `packages/federation/src/replicator-stub.ts` — PhaseOneReplicator (174 lines)
- `packages/federation/src/server.ts` — ServerContext (87 lines)
- `packages/federation/src/namespace.ts` — Namespace / ACL evaluator (158 lines)
- `packages/federation/src/vector-clock.ts` — VectorClock (103 lines)
- `packages/federation/src/region/types.ts` — Region interface (178 lines)
- `packages/federation/src/region/single-region.ts` — SingleRegion impl (103 lines)
- `packages/federation/src/mesh/postgres-sync-config.ts` (139 lines)
- `packages/federation/src/mesh/replication-monitor.ts` (152 lines)
- `packages/federation/src/crdts/g-counter.ts` (121 lines) + tagged-fraction + lww-register

### What it is

A **Phase 1 CRDT + data-model scaffolding layer**, NOT a network transport.
The `federation` package owns:

1. **CRDT primitives** — G-Counter, Tagged-Fraction, LWW-Register for
   volatile field merge (invocation counts, success rates, latencies).
2. **Mesh-level replication helpers** — Postgres sync-replication config
   generator and standby health classifier. No network code — pure logic that
   drives Postgres WAL replication (`postgres-sync-config.ts`, `replication-monitor.ts`).
3. **Server/Region/Namespace types** — `ServerContext` (read from env vars),
   `Namespace` with ACL evaluator, `Region` interface.
4. **`SingleRegion`** — Phase 1 default `Region` implementation that serves
   everything from local mesh (`single-region.ts`). No cross-region traffic.
5. **`PhaseOneReplicator` stub** — captures `onUpsert`/`onRemove` events into
   in-memory CRDT slots. `start()` and `stop()` are no-ops. Does NOT propagate
   to peers (`replicator-stub.ts:152-158`).

### What federation does NOT do (Phase 1)

The `index.ts` scope declaration explicitly lists these as out of scope:
- Kademlia DHT for cross-region (`libp2p-kad-dht` — Phase 2)
- CDC consumer (Postgres logical replication → CRDT view)
- Multi-region rollout
- DePIN cross-network discovery integration

### What federation federates

In Phase 1: **nothing leaves the process**. The `PhaseOneReplicator.onUpsert`
records CRDT deltas into `this.slots` (a `Map`) and increments
`this.pendingDeltas` as a counter — but never flushes them anywhere
(`replicator-stub.ts:88-90`).

The `Namespace` types and ACL evaluator are purely in-memory. The
`Region` interface defines the cross-region contract for Phase 2.

### Transport in federation

`@pcc/federation` depends on `@pcc/dht-core` (`package.json:7`) but does NOT
import `CoreTransport` anywhere in the current source. The dependency was
likely added in anticipation of Phase 2 Kademlia work.

**No network calls anywhere in the federation package today.**

## REUSE ASSESSMENT FOR 4 RTP TRANSPORTS

### Transport 1: LAN-relay (WiFi-relay in RTP)
Job dispatch to a kernel on the same LAN as the gateway, no public IP.

**What exists:**
- `CoreTransport` can `connect("ws://192.168.x.x:PORT")` — direct LAN WS
  (`dht-core/src/transport.ts:101-117`)
- `DHTTransport.addSocket(ws)` / `adoptSocket` can accept inbound connections
  from a locally-discovered device
- `AnnouncementRegistry` stores endpoints including LAN URLs
- Bootstrap config already supports `ws://` (non-TLS) LAN URLs
  (`bootstrap.ts:18-19`)

**Gaps:**
- No mDNS/Bonjour discovery (the `discover` gateway routes do mDNS, but that
  is in `packages/gateway`, not the DHT transport)
- No LAN relay forwarding — if the kernel is not directly reachable from the
  gateway, there is no relay chain
- DHT gossip assumes all connected peers are gateway-reachable

**Reusable:** `CoreTransport` (connection primitives), `AnnouncementRegistry`
(store LAN endpoint), `PeerEndpoint` type (url field holds LAN URL).

---

### Transport 2: Reverse-tunnel (persistent-websocket outbound from kernel to gateway)
Kernel behind firewall initiates WS to gateway; gateway dispatches jobs inbound.

**What exists:**
- Gateway `dht-ws.ts:49-61` already accepts inbound WS connections from kernels
  via `DHTNode.handleConnection(socket)` → `CoreTransport.adoptSocket(ws)`
- The gossip protocol already flows both directions over the same socket

**Gaps:**
- Only gossip messages (`DHTMessage`) flow over this socket — no job dispatch
  channel
- No multiplexed sub-streams (the `CoreMessage.protocol` field could be used
  to add a job-dispatch protocol alongside `cap-gossip/1.0.0`, but that code
  does not exist)
- No reconnect logic / backoff in `CoreTransport` — the kernel must reconnect
  manually on disconnect

**Reusable:** The inbound `adoptSocket` path, the `CoreMessage.protocol`
multiplexing field (add `"/pcc/job-dispatch/1.0.0"` as a second protocol on
the same connection).

---

### Transport 3: Persistent-websocket (bidirectional, long-lived)
Same as reverse-tunnel but potentially between two gateways or peer kernels.

**What exists:**
- `CoreTransport.connect(url)` dials outbound; `listen(port)` accepts inbound
- Messages are JSON-over-WebSocket (`CoreMessage`)
- `protocol` field multiplexes up to N protocols on one connection
- `PeerManager` tracks known peers with RTT and error counting

**Gaps:**
- No reconnect/keep-alive: `CoreTransport` does not re-dial on socket close
- No backpressure / flow control
- No message ordering guarantees (JSON order-of-send only)
- No authentication at the transport layer (auth happens at the Fastify route
  layer in `dht-ws.ts:52-56`, not in `CoreTransport` itself)

**Reusable:** `CoreTransport` as the entire frame transport. `PeerManager`
for tracking kernel connection state. The `CoreMessage` envelope with
`protocol` field as the multiplexing primitive.

---

### Transport 4: Decentralized messaging (XMTP / similar wallet-addressed p2p)
Messages addressed to wallet/DID, stored-and-forwarded, intermittent-link safe.

**What exists:**
- `PeerIdentity.did` (`p2p.ts:8`) can hold any DID including wallet-derived DIDs
- `CapabilityAnnouncement.endpoints` array can include non-WebSocket endpoint
  descriptors (the `TransportType` union already has `"http-poll"` and `"webrtc"`
  as stub types at `p2p.ts:50`)
- `AnnouncementRegistry` stores kernel endpoints — could include XMTP addresses

**Gaps:**
- No XMTP or any async/store-and-forward messaging implemented
- No wallet address → peer resolution
- `TransportType` lacks `"xmtp"`, `"mqtt"`, etc.
- No intermittent-link buffering — `CoreTransport.send()` drops silently if
  the socket is not `OPEN` (`transport.ts:132-136`)
- `EvidenceAnnouncement` contains IPFS CID + Lit conditions but these are
  stored locally only; no peer gossip for them (no `DHTMessage` type)

**Reusable:** `PeerIdentity` / `PeerEndpoint` type shapes (add new
`TransportType` values). `AnnouncementRegistry` could store XMTP-addressed
endpoints.

## HAS vs LACKS (transport purposes)

### HAS
- Working WebSocket transport primitive (`CoreTransport`) — TCP-framed, JSON,
  multi-protocol-muxed via `protocol` string field
- Gossip flood for capability discovery — announce/query/result round-trip
- Signed `CapabilityAnnouncement` with Ed25519 (`@pcc/a2a`) and TTL expiry
- Evidence IPFS CID registry slot (`storeEvidence`) — local only
- Peer allowlist mode (`PeerManager.allowlistMode`) — federation can whitelist
  specific peer regions
- Gateway WebSocket endpoint already live at `wss://capability.network/ws/dht`
- `protocol` field multiplexing — can carry a second protocol on the same
  connection without code changes to `CoreTransport`
- `adoptSocket` — accepts externally-provided sockets (from Fastify WS routes
  or any other framework)
- CRDT primitives in `@pcc/federation` for convergent state merge across nodes
- `VectorClock` and `LWWRegister` for ordering concurrent writes

### LACKS
- NAT traversal (TURN, STUN, hole-punching, relay forwarding)
- Reconnect / backoff logic in `CoreTransport`
- Job dispatch over DHT (no DHTMessage type for it; no request/response over WS)
- Evidence bundle transport (IPFS CID gossiping is coded but has no DHTMessage type)
- Wallet-addressed / decentralized messaging (XMTP, MQTT, LoRa)
- mDNS/LAN peer discovery (present in gateway `discover` routes, not in DHT package)
- Authentication at the `CoreTransport` level
- Backpressure / flow control
- Cross-region federation traffic (Phase 1 is single-region only)
- Kademlia routing (explicitly deferred to Phase 2)
