## SAST / Manual Code Review Findings

### MEDIUM — No TLS configuration in `NATSJetStreamBackendOptions`

**Location:** `feat/message-bus-nats` — `src/backends/nats-jetstream-backend.ts`

The `NATSJetStreamBackendOptions` interface exposes only `url`, `streamName`,
and reconnect tuning. There is no `tls`, `nkey`, `creds`, or `userCredentials`
field. The `doConnect()` call passes no auth options to `nats.js`. In a
production NATS JetStream deployment, this means all traffic flows plaintext
and unauthenticated unless the caller configures auth externally at the NATS
server level.

**Risk:** Medium — only exploitable if the NATS server is network-accessible.
Internal-only or loopback deployments are lower risk. Production deployments
must configure TLS at the NATS server or add auth options to this interface.

**Recommendation:** Extend `NATSJetStreamBackendOptions` with optional
`tlsOptions` and `authOptions` fields mirroring the `nats.js` `ConnectionOptions`
surface. Gate A does not FAIL on missing TLS config alone, but this should be
addressed before enabling on a public-network NATS endpoint.

### LOW — `nats@2.29.3` URL parameter accepts arbitrary `nats://` strings

**Location:** `src/backends/nats-jetstream-backend.ts:41`

The `url` field accepts any string, including `nats://attacker.example.com:4222`.
No validation or allowlisting is performed before connecting. Callers must
ensure the URL is operator-controlled; this is not a code defect per se, but
worth noting in the context of the broader PCC threat model (agent-submitted
capability parameters).
