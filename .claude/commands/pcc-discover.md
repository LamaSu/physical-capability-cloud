# PCC Discover — CLI

Device discovery, network scanning, and full operator onboarding — from zero to a registered, verified kernel.

## When to use
- "Help me onboard a new device"
- "Set up a kernel"
- "Scan the network for devices"
- "Register my 3D printer / CNC / HPLC on PCC"
- "Configure a new shop kernel"
- "Check if my device is set up correctly"
- "Run the setup wizard"
- "What's my setup status?"

## Prerequisites
- Build the CLI first: `cd packages/mcp-server && npx tsc`
- Gateway reachable at `PCC_URL` (default: https://pcc-gateway-production.up.railway.app)
- For device registration: the physical device must be network-accessible from the machine running the CLI

## Commands

### Discover Scan — Find Devices on the Network
```bash
node packages/mcp-server/dist/cli.js discover scan
```
Scans the local network using mDNS and IPP discovery to find devices (printers, CNC machines, lab instruments) that can be registered on PCC. Returns a list of discovered devices with their type, IP address, and auto-detected capability type. Run this first when adding new equipment.

### Discover Onboard — One-Command Auto-Onboarding
```bash
node packages/mcp-server/dist/cli.js discover onboard
```
Full pipeline in one command: scan → identify device → generate CSD → register on PCC. Best for standard equipment (OctoPrint printers, IPP-compatible devices). For custom or complex equipment, use the step-by-step setup commands below.

### Setup Detect — Check Configuration State
```bash
node packages/mcp-server/dist/cli.js setup detect
```
Auto-detects the current configuration state. Reports what's already set up (kernel config, registered devices, env file) and what's missing. Always run this first before starting a manual setup — it tells you exactly where to begin.

### Setup Config — Generate Kernel Configuration
```bash
node packages/mcp-server/dist/cli.js setup config
```
Interactively generates a `KERNEL_CONFIG` JSON from device descriptions. Asks about equipment type, adapter protocol (OctoPrint, Modbus RTU, OPC-UA, SiLA2), capabilities, and pricing. Outputs configuration you can save to `kernel-config.json` or set as `KERNEL_CONFIG_FILE`.

### Setup Register Device — Register a Physical Device
```bash
node packages/mcp-server/dist/cli.js setup register-device
```
Registers a physical device on the PCC network using the configuration generated by `setup config`. Creates the on-chain ERC-8004 identity for the device and returns its assigned device ID. Run after `setup config` and before `setup health`.

### Setup Health — Check Device Health
```bash
node packages/mcp-server/dist/cli.js setup health
```
Runs connectivity and capability checks on registered devices. Verifies:
- Network reachability of each device
- Protocol adapter connection (OctoPrint API, Modbus registers, OPC-UA node, SiLA2 service)
- Sensor channels are readable
- Device is ready to accept jobs

### Setup Test Job — Run a Test Job
```bash
node packages/mcp-server/dist/cli.js setup test-job
```
Submits a synthetic test job through the full pipeline: contract → escrow → kernel execution → evidence → settlement. Validates that the entire flow works end-to-end before you start accepting real jobs. Safe to run — no on-chain funds are moved for test jobs.

### Setup Status — Overall Setup Status
```bash
node packages/mcp-server/dist/cli.js setup status
```
Comprehensive status dashboard across all setup categories: gateway connectivity, kernel config, registered devices, adapter health, evidence pipeline, and DePIN enrollment. Shows a checklist of what's green/yellow/red.

### Setup Env — Generate .env File
```bash
node packages/mcp-server/dist/cli.js setup env <profile>
```
Generates a `.env` file pre-filled for a specific profile. Profiles:
- `dev` — local development with mock adapters, no on-chain state
- `testnet` — Base Sepolia + Lit datil-test, real network but no real money
- `mainnet` — production configuration with all real services

Example:
```bash
node packages/mcp-server/dist/cli.js setup env testnet
```

### Setup Validate — Validate Configuration
```bash
node packages/mcp-server/dist/cli.js setup validate
```
Validates the current `KERNEL_CONFIG` or config file for schema correctness, required fields, and cross-field consistency (e.g., assurance tier 2+ requires bond fields). Run before deployment to catch config errors early.

## Workflow: Full New Device Onboarding (Manual, Step-by-Step)

For standard plug-and-play devices, use `discover onboard`. For custom equipment, follow these steps:

1. Check what's already configured:
   ```bash
   node packages/mcp-server/dist/cli.js setup detect
   ```

2. Scan the network to see if the device is discoverable:
   ```bash
   node packages/mcp-server/dist/cli.js discover scan
   ```

3. Generate kernel configuration for the device:
   ```bash
   node packages/mcp-server/dist/cli.js setup config
   ```

4. Validate the generated configuration:
   ```bash
   node packages/mcp-server/dist/cli.js setup validate
   ```

5. Generate the appropriate .env file:
   ```bash
   node packages/mcp-server/dist/cli.js setup env testnet
   ```

6. Register the device on-chain:
   ```bash
   node packages/mcp-server/dist/cli.js setup register-device
   ```

7. Verify device health and adapter connectivity:
   ```bash
   node packages/mcp-server/dist/cli.js setup health
   ```

8. Run a test job through the full pipeline:
   ```bash
   node packages/mcp-server/dist/cli.js setup test-job
   ```

9. Confirm everything is green:
   ```bash
   node packages/mcp-server/dist/cli.js setup status
   ```

## Workflow: Quick Auto-Onboard (OctoPrint / IPP Devices)

For OctoPrint printers and IPP-compatible devices, skip the manual steps:

1. Ensure the device is on the same network, then:
   ```bash
   node packages/mcp-server/dist/cli.js discover onboard
   ```

2. Confirm the result:
   ```bash
   node packages/mcp-server/dist/cli.js setup status
   ```

## Tips
- Always run `setup detect` first — it tells you exactly what to do next and saves time.
- `setup validate` is cheap to run repeatedly during config editing. Run it after every change.
- The `testnet` env profile is the safest starting point — it uses real network infrastructure but no real funds.
- If `setup health` reports adapter connectivity failures, check the device's IP/port first. Most failures are network routing issues, not PCC config problems.
- `setup test-job` is the true end-to-end smoke test. Only trust `setup status` fully after this passes.
- Device IDs returned by `register-device` are permanent on-chain identifiers — store them in your notes.
